There are a wide range of ways to set up your Umbraco sites with an equally wide range of platforms and hosting solutions to choose from. 

## Causes of Common Issues 
When people contact us with an issue connecting two Umbraco sites with uSync.Publisher we often find it is caused by one of the following problems.

## 1. Load Balancing

During any push or pull operation uSync sends a sequence of requests to a target server, and
each one relies on files the previous request left behind. If that sequence of requests lands on
different servers behind a load balancer (round-robin, say), the working files won't be there and
you'll see a 'File not found' or 'Folder missing' error partway through.

:::tip
If you see a 'File not found/Folder missing' error and you think your site is not load balanced, you should check. It could be load balanced in some way you are not aware of.
:::

uSync has built-in support for keeping a push or pull pinned to one server (**server affinity**),
so this no longer means you have to run the backoffice without load balancing.

### Server affinity

When a target server sets a cookie on its response - an ARR affinity cookie, an Application
Gateway cookie, or whatever your load balancer uses - uSync remembers it and sends it back on
every later request of the same push or pull, keeping the whole operation pinned to the server
that answered first.

This is on by default and works with any load balancer's own affinity cookie - uSync doesn't
need to be told the cookie's name.

```json title='appsettings.json'
{
  "uSync": {
    "Publisher": {
      "Settings": {
        "AffinityEnabled": true,
        "AffinityCookieNames": [],
        "AffinityFailFast": false
      }
    }
  }
}
```

#### AffinityEnabled
<!--| true/false |-->
Turns server-affinity cookie handling on or off. On by default - it only does anything once a
target actually sets a cookie, so it's a no-op against a single, non-load-balanced server.

#### AffinityCookieNames
<!--| string[] |-->
Cookie names to remember and replay. Leave this empty (the default) to replay every cookie the
target sets - the simplest option, and it works with any load balancer without needing to know
its cookie's name. Only set this if a target sets other cookies that should specifically be left
alone.

#### AffinityFailFast
<!--| true/false |-->
If a push or pull's requests stop reaching the same server partway through, uSync always logs a
warning naming the two servers. Turn this setting on to also abort the operation right there,
instead of letting it run for several more steps and fail with a confusing 'missing pack folder'
error. Off by default.

### A shared working folder

Server affinity keeps requests going to the same server, but the reason it matters at all is
that each server keeps its working files - uploaded pack files, an in-progress import - on its
own local, temporary storage.

If your servers can see shared storage - a UNC share, a mounted volume, or (on Azure) a path
backed by Azure Files - you can point uSync's working folder at it, so every server sees the same
files:

```json title='appsettings.json'
{
  "uSync": {
    "WorkingFolder": {
      "Path": "\\\\shared-server\\usyncwork"
    }
  }
}
```

`Path` also accepts a `~/` path relative to your site's content root. Leave it unset (the
default) and nothing changes.

:::tip
This is read once when the site starts, the same way Umbraco's own temp folder setting is -
changing it while the site is running has no effect until it restarts.
:::

### Diagnosing an affinity issue

Every response from a uSync receive endpoint carries an `X-uSync-Node` header identifying which
server actually answered it. If a push or pull's requests stop landing on the same server, uSync
logs a warning naming the two servers and the step it happened on - turn up
[uSync logging](../../uSync/guides/debugging) to see it.

### What this doesn't cover

- **The connection between your browser and the source site** still needs its own affinity if
  the *source* itself is load balanced - this is ordinary load-balancer session affinity (the
  kind most load balancers already provide for any logged-in session), not something uSync
  configures.
- **Progress updates** - the live progress bar during a push or pull - use a separate connection
  that doesn't always follow the same server as the main requests. This only affects how chatty
  the progress bar is, never whether the operation itself succeeds. If it becomes a problem, turn
  it off:

```json title='appsettings.json'
{
  "uSync": {
    "Publisher": {
      "Settings": {
        "ServerToServerHub": false
      }
    }
  }
}
```

*Operations are batched to avoid timeout issues on large site publish/syncing*

## 2. Firewall Issues 
There can be many settings on a firewall that can prevent uSync request getting through to a server:

### Blocking by URL 
uSync requests go to a URL starting `umbraco/uSyncReceive`. This is **not** a backoffice request URL. Blocking access to all `umbraco/` requests will stop uSync.Publisher from working. You should at least allow requests to URLs starting with this path (from safe IP Addresses).

### Blocking Request Types 
During a publish or pull action uSync will send requests using the GET and POST methods. Sometimes firewalls will block POST requests and the process will fail. This usually happens at the upload step.

### Blocking of Filetype Uploads
During a publish, uSync.Publisher will send a number of `.zip` files to the target server. If your firewall or proxy is configured to filter out zip file requests then these requests might fail. 

### Blocking by RequestHeaders or UserAgentString
Some firewalls will check the RequestHeaders or UserAgentString fields in a request. If they are blank, or set to certain values, the request will be blocked. To stop this, you need to fill in the UserAgentString and RequestHeaders fields. You can use the config settings to set these values for your requests. 

For example:

```json
"UserAgentString" : "uSync agent",
"RequestHeaders": {
   "header one": "custom value one",
   "header two": "custom value two"
}
```
## 3. Hostname Issues 

Sometimes a site's SSL certificate to be placed on proxy or host in front of the actual Umbraco site. Requests may go to **https**://www.mysite.com but when they arrive at the server the SSL certificate will have been removed and requests will appear to be to **http**://www.mysite.com. 

### a. Use baseUrl Setting

In this situation you should set the [baseURL setting](../guides/syncPublisher/publishConfig/send) for a server to be the actual address requests are sent to. 


### b. Disable Host Checking 
If you think the issue may be related to hostnames but cannot use the BaseUrl setting you can instruct uSync.Complete not to include the intended hostname in the signature when checking requests. 

*This is theoretically slightly less secure because intercepted requests for one server could be replayed onto another, but if you are securing the route between your servers this should not be an issue.*

Disable host in signature

```
"uSync": {
    "Publisher": {
      "Settings": {
        "IncomingEnabled": true,
        "AppId": "XXXXXXXXXXXXX",
        "AppKey": "XXXXXXXXXXXXXX",
        "IncludeHost": false
      }
    }
}
```

## Turn Up The Logging 
If you are unsure what is causing an issue you should turn up the logging on uSync to capture more information about what is going on. 

[Turn on uSync logging](../../uSync/guides/debugging)

### Logging Tips

#### 1. No Logging 
If after turning up the logging you see nothing being debugged on the target site, there is probably a network issue stopping the requests reaching the server.

#### 2. Connection Mismatches 
If you see mismatched signature errors in the logging then it is almost certainly a hostname issue. Try either using the baseUrl or disabling the `IncludeHost` setting for your sites. 

#### 3. Missing Files/Folders in the Logging
If the logging is reporting missing files or folders then your issue is probably [load-balancing related](#1-load-balancing). Check for a warning naming a change of server (an `X-uSync-Node` mismatch) just before the error - that confirms it, and tells you the operation lost server affinity partway through, rather than never having it in the first place.
